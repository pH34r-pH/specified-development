# Authoring and using the lifecycle

Research and ideas stayed in free-form Markdown outside canonical product authority until accepted into a mature design. Each optional proof of concept recorded a decision that it could invalidate, the smallest useful experiment, its stopping condition, and evidence. Spec authors described the full intended product directly in past tense. Explicit target and approval fields accompanied separate implementation, test, deployment, and regeneration evidence.

Authors edited `spec/` and chose stable feature IDs. A deterministic guard discovered the entire tree, validated every declared document/link/asset, and assembled the selected feature's normative closure. Approval froze source hashes and an accepted revision. A planner produced `build/<feature>/plan.md`; independent expected behavior became `tests.md`; semantic decomposition then produced `tasks.md` and complete structured metadata. Each step required fresh accepted upstream artifacts.

The compatibility `build/<feature>/spec.md` was labeled generated, read-only, and derived. It carried source IDs, input hashes, and a source map. Canonical edits went through replacement specify/clarify commands to `spec/`; direct edits to generated adapters were rejected. Existing domain constitutions remained consumer-owned authority and were included in frozen inputs.

The selected existing executor claimed dependency-ready leaves only after exact accepted inputs, native parent outputs, selected-model admission, capability-profile requirements, and permissions were verified; unexposed optional effective settings/usage remained explicit. A missing design assumption stopped that attempt and produced a separate bounded repair task at the earliest authority. Models never changed mid-attempt. Deterministic validation, projection, scheduling in the existing owner, and cache/cost accounting used scripts after this design's semantic decomposition.

## Prior-art review before plan authoring

Before finalizing a plan, review existing standards, algorithms, data structures, patterns, or compatible library interfaces when they could materially affect correctness, compatibility, security, expected performance or cost at the intended scale, or maintenance. Start with the workload: input size and growth, operation mix, update rate, and ordering needs. Then state the required invariants and observable failure semantics; choose the simplest suitable standard-library or existing-project baseline; and compare it with one or two plausible alternatives. Record time and space tradeoffs, implementation and maintenance burden, compatibility, and relevant boundary behavior. Cite sources for asymptotic bounds and label empirical performance claims separately; an empirical claim needs qualified measurement evidence. Do not use asymptotic improvements to justify complexity until the workload and scale make the relevant operations material.

A few recurring questions can help find candidates; use only the rows relevant to the design. This is a set of prompts, not a required checklist or an exhaustive catalog.

| Workload shape | Starting point and evidence to record |
| --- | --- |
| Keyed lookup, aggregation, or membership | Use a map for key-to-value access and a set for membership or visited identities. State key equality/hash assumptions, ordering requirements, and the extra index space; make output order explicit rather than relying on incidental enumeration. |
| Reachability or a frontier | Use a FIFO queue when arrival order is the rule, or a stack/DFS when depth-first exploration fits. Track visited/active state where cycles or repeated paths matter. Separate traversal work from any sorting used for deterministic discovery. |
| Repeatedly choose the best currently available item | A heap/priority queue fits a changing frontier with repeated minimum/maximum selection. Specify priority ties, stale/deleted entries, and queue space; a simple scan or sort may be cheaper for a small or one-shot workload. |
| Prerequisites or precedence | Model dependencies as a DAG only after validating every reference. Specify dependency-first order, ready-node tie policy, cycle failure, and whether partial progress is forbidden. Keep this graph distinct from task-execution scheduling unless the execution contract says otherwise. |
| Repeated range queries over ordered values | Compare a scan with sorting once and binary-searching ranges. Include sorting/setup cost and memory, the query count, and the cost of later insertions or mutation; binary search requires the searched sequence to remain sorted. |
| Repeated subproblems | Dynamic programming fits when a recurrence revisits a bounded set of subproblems. State the state definition and recurrence, then compare recomputation with memo/table space and lifetime. |
| Locally best choice or shortest path | A greedy method needs a correctness argument for its choice rule. Match shortest-path algorithms to their preconditions; for example, Dijkstra requires nonnegative edge weights. A familiar algorithm name does not establish that its assumptions hold. |
| Shared work or durable state | Add concurrency only with clear ownership, independent-ready work, completion ordering, and failure handling. Persist state only when restart, audit, or recovery requirements need it; specify atomicity, retention, and recovery boundaries. |

For algorithm analysis, useful starting references include Donald E. Knuth, [*The Art of Computer Programming*, Vol. 1, *Fundamental Algorithms*, 3rd ed.](https://cs.stanford.edu/~knuth/taocp.html), and Cormen, Leiserson, Rivest, and Stein, [*Introduction to Algorithms*, 4th ed.](https://mitpress.mit.edu/9780262046305/introduction-to-algorithms/). TAOCP is an algorithm/data-structure reference, not an architecture-pattern catalog. For the current topics, the consulted CLRS table of contents identifies §§6.5 “Priority queues,” 14.3 “Elements of dynamic programming,” 15.2 “Elements of the greedy strategy,” 20.4 “Topological sort,” and 22.3 “Dijkstra’s algorithm”; do not infer guidance from unconsulted sections. Versioned API behavior belongs to the selected language and runtime: see the Python 3.12 docs for [`collections`](https://docs.python.org/3.12/library/collections.html), [`bisect`](https://docs.python.org/3.12/library/bisect.html), [`graphlib`](https://docs.python.org/3.12/library/graphlib.html), and [`heapq`](https://docs.python.org/3.12/library/heapq.html) when those APIs are actually relevant. These API pages do not replace language-neutral algorithm analysis.

For a material choice, keep the record compact: the requirement and workload; where the candidate applies and does not; assumptions/invariants and failure behavior; a simple baseline plus one or two alternatives; why each is selected or rejected; and composition effects on side effects, state ownership, concurrency, and compatibility. Record the source, edition/version, and section or stable URL actually consulted. A book, standard, or API citation is not a license to copy code. If code or a package is actually reused, record its exact version and license compatibility separately. Trivial choices need no citation or decision record. If no useful prior art applies, say so briefly rather than inventing a pattern. Trace material assumptions and composition risks to an existing independent oracle, or explain why no new oracle is warranted. During task review, keep expected behavior anchored to accepted requirements and independent expected results; do not derive an oracle from the implementation choice. Deterministic tests do not substantiate empirical performance claims. Do not build a universal pattern or algorithm catalog.

## Implementation finish and refinement

Closeout separates behavior acceptance from implementation review. First confirm the accepted behavior against the unchanged independent oracle, focused regressions, and exact-head CI evidence. Then review whether names and boundaries make intent clear, dependencies and abstractions are warranted, and error paths, state changes, side effects, and test failures are understandable. For a cleanup to count as behavior-preserving, compare observable outputs and ordering, failure results, and side effects against the accepted behavior; do not infer equivalence from a structural-looking diff. Keep cleanup within the task's declared scope, make bounded changes, and rerun the unchanged oracle and focused regressions after cleanup. Record the exact-head check result and any cleanup or remaining review item. Do not use a style linter or numeric method, line, or function limits as a substitute for review.

If behavior differs from the accepted contract, stop the attempt and route the discovery to the earliest canonical authority; review or invalidate only affected downstream artifacts and native descendants under the freshness rules. A behavior-preserving refinement does not by itself require rewriting specifications or task records. A CI failure gets only the bounded repair allowed by the task's existing attempt policy; a scope or design gap becomes a separate repair rather than an unreviewed expansion.

These review prompts draw on Robert C. Martin, [*Clean Code: A Handbook of Agile Software Craftsmanship*, 2nd ed.](https://www.pearson.com/en-us/subject-catalog/p/clean-code-a-handbook-of-agile-software-craftsmanship-2nd-edition/P200000013239/9780135398548), whose publisher overview describes naming, error handling, testing, and dependency management. The behavior-preserving distinction is also consistent with Martin Fowler and Kent Beck, [*Refactoring: Improving the Design of Existing Code*, 2nd ed.](https://martinfowler.com/books/refactoring.html). These are review prompts, not reproduced book rules, passages, code, or numeric thresholds; no unconsulted chapter guidance is claimed.

Plans/tasks/issue bindings/receipts remained durable after acceptance even though their paths began with `build/`. Candidate/current rendering could be replaced; immutable accepted revisions could not. Retained code remained available. Scoped behavioral regeneration required independent clean workspaces and oracles before a scoped disposability claim; no source deletion followed from that claim.

Documentation displayed the canonical Markdown content. A local rendered site and optional authorized wiki export rewrote only navigation, links, anchors where renderer rules required, and asset locations. Wiki edits created detectable drift; a correction returned to canonical `spec/` before one-way regeneration.
