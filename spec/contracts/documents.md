# Document compilation contract

## Source inventory and identity

`spec/manifest.json` schema version 1 defines `documents` keyed by stable document ID (`path`, `role`, `normative_dependencies`, `assets`), feature roots, and assets keyed by stable asset ID (`path`, `media_type`). `spec/navigation.json` is a presentation tree of document IDs with labels. Control files are inventory-known but not product prose. All regular files below spec are registered documents, assets or the two control files; undiscovered or unregistered files fail validation. Research stays outside spec until explicitly incorporated.

Feature IDs match `[a-z0-9]+(?:-[a-z0-9]+)*`. Document and asset IDs match `[a-zA-Z0-9][a-zA-Z0-9._/-]*`, with no empty or dot path segment. IDs are unique case-sensitively and case-fold collisions are rejected for portability. Relative POSIX paths are confined beneath spec; traversal, symlinks, absolute local references, duplicate normalized/case-fold paths and reserved wiki names fail. Normative dependencies reference registered document IDs and form an acyclic input-selection graph. The graph is never used for execution readiness.

Each feature lists a root and any explicit common entrypoints. Depth-first discovery follows lexicographically sorted IDs, then emits dependency-first topological order with ID tie-breaks. Document links are resolved independently of navigation. A requirement-bearing cross-reference to another document requires a manifest dependency; ordinary presentation links can leave closure. Normative references use explicit `<!-- normative-ref: document-id#requirement-id -->` annotations adjacent to Markdown links. Missing annotations for requirement or schema citations fail; all fragments need an actual target. Stable requirement IDs are plain visible identifiers; link fragments follow qualified renderer rules, never an assumed portable HTML extension.

Assets are included only from selected document asset lists and validated content references. Unused or undeclared referenced assets fail. Full discovery inventory detects additions and deletions; selected semantic hashes remain separate, so unrelated changes trigger revalidation but not automatic staleness of unchanged task contracts.

## Assembly and source map

The compiler emits UTF-8 LF metadata/preamble, a read-only derived warning, selected source paths/IDs/hashes, then exact UTF-8 source bytes with deterministic document boundary headings. Input source bytes are neither summarized nor rewritten. Invalid encoding fails; a trailing separator is outside source byte ranges. Source-map JSON identifies document ID, path and hash and half-open byte ranges in both adapter and original. Boundaries and metadata are separately mapped as generated bytes. Golden fixtures fix order, line endings, ranges and digest; tests compare original slices, not compiler-produced expected prose.

`inputs.lock.json` schema version 1 records discovery inventory hashes, normalized manifest and closure IDs/order, all selected byte hashes and assets, consumer authority and tool/lock fingerprints, adapter/map hashes, exact upstream commit, component/template/projector versions and digests, and accepted source revision. Self-hashes are excluded from their own hash calculation; the lock root is the SHA256 of canonical JSON with sorted keys, UTF-8 and no insignificant whitespace. The adapter preamble contains the input-root hash, not its own future digest. A missing mandatory digest or unknown runtime field prohibits freshness and acceptance claims.

Assembly stages files on the same filesystem, validates every output and before-hash comparison, then journals promotion. No accepted snapshot is replaced. Partial failure retains the stage and journal and restores previous managed bytes and modes; recovery proof is required. Canonical sources are never symlinked into build.

## Upstream integration and command surface

The extension exposes deterministic `ph34r-spec documents validate`, `assemble --feature ID`, `check --feature ID`, `clean --feature ID --dry-run`, `site --check`, `wiki --dry-run` and controlled `wiki --apply`. These are planned extension-owned verbs, not unsupported upstream CLI flags. Every execute path validates accepted inputs and current effective assets before delegating.

The wrapper resolves the repository root, validates feature identity, assembles the adapter, sets `SPECIFY_FEATURE_DIRECTORY=build/<feature>` and `SPECIFY_FEATURE_NO_PERSIST=1`, and reuses upstream primitives. Presets replace specify/clarify to edit canonical source, and replace plan/tasks/analyze/implement assumptions to use adapters and source maps. The independent-tests semantic command precedes task decomposition. Every active integration's installed command assets are hash-verified. Bypass via known unsupported stock commands fails with a repair/installation diagnostic; an arbitrary external tool can still write files, so CI independently rejects drift.

Command guards do not launch a model. Semantic authoring runs in the selected existing executor with one approved exact model selection and parent/service admission; deterministic script verbs use no inference. Requested reasoning and speed settings and their parent/service admission are retained separately from available effective observations. Capability profiles distinguish advisory work from hard-limit and measurement requirements; unsupported flags are not invented.

## Documentation projection

The repository view uses source relative links. A qualified pinned MkDocs build uses `docs_dir: spec`, `site_dir: build/site` and deterministic navigation derived from navigation.json. The extension treats this as an optional capability: exact renderer/plugin versions, hashes, output behavior and asset inventory need qualification; no version is guessed at design time.

Wiki page names use a reversible injective map from stable document IDs, with explicit Home/sidebar and reserved-name handling. Path, anchor and asset rewrites are deterministic; source prose tokens and asset byte digests are preserved. Renderer anchor mappings come from verified golden examples for the exact renderer, including duplicate headings and non-ASCII, and are stored in export evidence. Colliding page, asset or fragment maps fail before publication. Export carries source IDs/hash and projection version. The GitHub wiki is a separate Git repository; actual availability and access are checked before authorized publication. Wiki remote inventory/base hash has compare-and-swap semantics; any unmanaged edit or divergent managed page blocks apply and produces a canonical-repair packet. No automatic reverse sync occurs.

Public export includes only manifest-public documents and assets after secret/private-path scanning and human review of the concrete allowlist. Model rewriting is never part of rendering. Local site and wiki builds are reversible; actual wiki, Pages or release deployment needs its own explicit authorization.
