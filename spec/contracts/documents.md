# Document compilation contract

## Source inventory and identity

`spec/manifest.json` schema version 1 defined `documents` keyed by stable document ID (`path`, `role`, `normative_dependencies`, `assets`), feature roots, and assets keyed by stable asset ID (`path`, `media_type`). `spec/navigation.json` was a presentation tree of document IDs with labels. Control files were inventory-known but not product prose. All regular files below spec were registered documents, assets, or the two control files; undiscovered/unregistered files failed validation. Research stayed outside spec until explicitly incorporated.

Feature IDs matched `[a-z0-9]+(?:-[a-z0-9]+)*`. Document/asset IDs matched `[a-zA-Z0-9][a-zA-Z0-9._/-]*`, with no empty or dot path segment. IDs were unique case-sensitively and case-fold collisions were rejected for portability. Relative POSIX paths were confined beneath spec; traversal, symlinks, absolute local references, duplicate normalized/case-fold paths and reserved wiki names failed. Normative dependencies referenced registered document IDs and formed an acyclic input-selection graph. The graph was never used for execution readiness.

Each feature listed a root and any explicit common entrypoints. Depth-first discovery followed lexicographically sorted IDs, then emitted dependency-first topological order with ID tie-breaks. Document links were resolved independently of navigation. A requirement-bearing cross-reference to another document required a manifest dependency; ordinary presentation links could leave closure. Normative references used explicit `<!-- normative-ref: document-id#requirement-id -->` annotations adjacent to Markdown links. Missing annotations for requirement/schema citations failed; all fragments needed an actual target. Stable requirement IDs were plain visible identifiers; link fragments followed qualified renderer rules, never an assumed portable HTML extension.

Assets were included only from selected document asset lists and validated content references. Unused/undeclared referenced assets failed. Full discovery inventory detected additions/deletions; selected semantic hashes remained separate, so unrelated changes triggered revalidation but not automatic staleness of unchanged task contracts.

## Assembly and source map

The compiler emitted UTF-8 LF metadata/preamble, a read-only derived warning, selected source paths/IDs/hashes, then exact UTF-8 source bytes with deterministic document boundary headings. Input source bytes were neither summarized nor rewritten. Invalid encoding failed; a trailing separator was outside source byte ranges. Source-map JSON identified document ID/path/hash and half-open byte ranges in both adapter and original. Boundaries and metadata were separately mapped as generated bytes. Golden fixtures fixed order, line endings, ranges and digest; tests compared original slices, not compiler-produced expected prose.

`inputs.lock.json` schema version 1 recorded discovery inventory hashes, normalized manifest and closure IDs/order, all selected byte hashes/assets, consumer authority and tool/lock fingerprints, adapter/map hashes, exact upstream commit, component/template/projector versions/digests, and accepted source revision. Self-hashes were excluded from their own hash calculation; lock root was SHA256 of canonical JSON with sorted keys, UTF-8, no insignificant whitespace. The adapter preamble contained the input-root hash, not its own future digest. A missing mandatory digest or unknown runtime field prohibited freshness/acceptance claims.

Assembly staged files on the same filesystem, validated every output and before-hash comparison, then journaled promotion. No accepted snapshot was replaced. Partial failure retained the stage/journal and restored previous managed bytes/modes; recovery proof was required. Canonical sources were never symlinked into build.

## Upstream integration and command surface

The extension exposed deterministic `ph34r-spec documents validate`, `assemble --feature ID`, `check --feature ID`, `clean --feature ID --dry-run`, `site --check`, `wiki --dry-run`, and controlled `wiki --apply`. These were planned extension-owned verbs, not unsupported upstream CLI flags. Every execute path validated accepted inputs and current effective assets before delegating.

The wrapper resolved repository root, validated feature identity, assembled the adapter, set `SPECIFY_FEATURE_DIRECTORY=build/<feature>` and `SPECIFY_FEATURE_NO_PERSIST=1`, and reused upstream primitives. Presets replaced specify/clarify to edit canonical source and plan/tasks/analyze/implement assumptions to use adapters/source maps. The new independent-tests semantic command preceded task decomposition. Every active integration's installed command assets were hash-verified. Bypass via known unsupported stock commands failed with a repair/installation diagnostic; an arbitrary external tool could still write files, so CI independently rejected drift.

Command guards did not launch a model. Semantic authoring ran in the selected existing executor with one observed exact model; deterministic script verbs used no inference. Requested reasoning/speed settings were preserved as requirements and actual evidence; unsupported flags were not invented.

## Documentation projection

Repository view used source relative links. A qualified pinned MkDocs build used `docs_dir: spec`, `site_dir: build/site` and deterministic navigation derived from navigation.json. The extension treated this as optional capability: exact renderer/plugin versions, hashes, output behavior and asset inventory needed qualification; no version was guessed at design time.

Wiki page names used a reversible injective map from stable document IDs, with explicit Home/sidebar and reserved-name handling. Path/anchor/asset rewrites were deterministic; source prose tokens and asset byte digests were preserved. Renderer anchor mappings came from verified golden examples for the exact renderer, including duplicate headings and non-ASCII, and were stored in export evidence. Colliding page/asset/fragment maps failed before publication. Export carried source IDs/hash and projection version. The GitHub wiki was a separate Git repository; actual availability/access were checked before authorized publication. Wiki remote inventory/base hash had compare-and-swap semantics; any unmanaged edit or divergent managed page blocked apply and produced a canonical-repair packet. No automatic reverse sync occurred.

Public export included only manifest-public documents/assets after secret/private-path scanning and human review of the concrete allowlist. Model rewriting was never part of rendering. Local site/wiki build was reversible; actual wiki/Pages/release deployment needed its own explicit authorization.
